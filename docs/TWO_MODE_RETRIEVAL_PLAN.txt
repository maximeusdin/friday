================================================================================
KEY DESIGN DECISIONS
================================================================================

MODE PRECEDENCE (highest to lowest)
-----------------------------------
1. UI toggle - explicit user selection in interface
2. Primitive override - SET_RETRIEVAL_MODE in plan
3. Trigger phrase detection - "exhaustive", "everything", etc.
4. Default - conversational

VECTOR SIMILARITY SEMANTICS
---------------------------
Store explicit metric configuration to avoid formula breakage:
- vector_metric: "cosine" | "l2" | "ip"
- vector_operator: "<=>" | "<->" | "<#>"
- similarity_transform: e.g., "1 - cosine_distance" for cosine

Note: pgvector's <=> is cosine distance. Similarity = 1 - distance, range
[-1, 1]. Thresholds must account for possible negative similarity with
opposite-direction embeddings.

UI/Mental Model Alignment:
- Internal: threshold in actual similarity space [-1, 1]
- UI option: present as "precision slider" (0-100%) or "strictness"
- Alternative: accept [0,1] in UI, transform internally via (2x - 1)
- Store both raw_threshold (user-facing) and effective_threshold (internal)
- Primitive SET_SIMILARITY_THRESHOLD accepts internal scale [-1, 1]

PAGINATION STRATEGY
-------------------
- Offset pagination: Simple, fine for small result sets
- Cursor pagination: Required for thorough mode scalability (after_rank param)
- Both supported; cursor is the scalable path for large result sets

AUDIT TRAIL INTEGRITY
---------------------
Critical invariant: every result_set has exactly one retrieval_run receipt.
- result_sets.retrieval_run_id is NOT NULL (enforced in schema)
- Never create result_set without a run
- Optional: include retrieval_run_id as redundant column in traces for direct
  run queries (simplifies debugging, not required for correctness)

MATCH TRACE STORAGE
-------------------
Split into "hot" columns for fast queries + JSONB audit log:
- Hot: matched_entity_ids int[], matched_phrases text[], scope_passed boolean
- Cold: primitive_matches JSONB (full audit detail)
- Compact filter traces: applied_filters[] list at RUN level, not per-chunk

Note on scope_passed: Any chunk in the result set has passed scope filters
(otherwise it wouldn't be included). So scope_passed is always TRUE for
included results. Only store failed_filters if you explicitly compute
exclusion analysis ("why didn't X appear?"). For now, scope_passed is
redundant but kept for schema clarity; may remove later.

RANKING POLICIES (Precise Definition)
-------------------------------------
Conversational mode:
  - Rank = final ordering after hybrid scoring + tie-breakers
  - ORDER BY: score_hybrid DESC, chunk_id ASC
  - Rank assigned after RRF fusion, before cap

Thorough mode:
  - Rank = deterministic ordering by (document_id, chunk_id)
  - No score-based ranking - keeps exhaustive results neutral
  - Requires: every chunk has document_id (from chunk metadata)

Handling NULL document_id:
  - Chunks without document_id: sort LAST using sentinel
  - SQL: ORDER BY COALESCE(document_id, 2147483647), chunk_id
  - Do NOT exclude them from thorough results
  - Investigate and fix any chunks missing document_id (data quality issue)

RERUN SEMANTICS
---------------
- Idempotent by default: reuse existing result_set unless force_rerun=True
- New execution creates new result_set (audit trail preserved)
- PKs prevent duplicate rows

INDEX STRATEGY (Deferred vs Immediate)
--------------------------------------
Immediate indexes:
- (result_set_id, chunk_id) PK on traces - required
- (result_set_id, rank) on result_set_chunks - required for cursor pagination
- (entity_id, chunk_id) on entity_mentions - required for NOT EXISTS

Deferred indexes (create when needed):
- GIN on matched_entity_ids - only if you need "find traces where entity X
  surfaced" queries; entity aggregation uses entity_mentions, not traces
- GIN on primitive_matches JSONB - defer until audit queries are common

RRF IMPLEMENTATION STRATEGY
---------------------------
Default: SQL CTE approach (not Python dict)
- Deterministic
- Faster (no large set pulls into Python)
- Works for both conversational and thorough candidate pools
- Python fallback only for special cases or debugging

TIERED ENRICHMENT HARD RULES
----------------------------
| Tier | When         | What                                     |
|------|--------------|------------------------------------------|
| 0    | All results  | Hot columns from search (scores, ranks)  |
| 1    | All results  | Entity IDs from entity_mentions (batch)  |
| 2    | Top N only   | Full entity details for LLM synthesis    |
| 3    | On-demand    | Phrase positions, full text highlights   |

HARD RULE: Never load full chunk text for more than summarization_limit
chunks during execution, even in thorough mode. Thorough mode returns all
chunk IDs but does NOT do LLM prep work for all of them.

def resolve_retrieval_mode(
    ui_toggle: str | None,
    primitive_mode: str | None, 
    utterance: str
) -> tuple[Literal["conversational", "thorough"], str]:
    """
    Resolve final mode with precedence: ui_toggle > primitive > trigger > default.
    Returns (mode, source) where source is 'ui_toggle'|'primitive'|'trigger_phrase'|'default'.
    """
    if ui_toggle:
        return ui_toggle, "ui_toggle"
    if primitive_mode:
        return primitive_mode, "primitive"
    detected = detect_retrieval_mode(utterance)
    if detected == "thorough":
        return "thorough", "trigger_phrase"
    return "conversational", "default"

4.2 RANKING POLICY
------------------

Critical: Union/intersection yields sets; ranking policy determines order.

IMPORTANT BUG TO AVOID: Never use list(set).index(chunk_id) to compute ranks.
Converting a set to a list destroys ordering and produces random-ish ranks.
Always carry ranks explicitly from SQL queries.

Conversational Mode Ranking:

def compute_conversational_rank(
    score_lex: float | None,
    score_vec: float | None,
    chunk_id: int,
    weights: tuple[float, float] = (0.5, 0.5),
) -> tuple[float, int]:
    """
    Returns (score, tiebreaker) for ORDER BY score DESC, chunk_id ASC.
    """
    norm_lex = normalize_lexical_score(score_lex) if score_lex else 0.0
    norm_vec = normalize_vector_score(score_vec) if score_vec else 0.0
    combined = weights[0] * norm_lex + weights[1] * norm_vec
    return (combined, chunk_id)  # chunk_id for deterministic tie-break

Thorough Mode Ranking:

def compute_thorough_rank(document_id: int, chunk_id: int) -> tuple[int, int]:
    """
    Deterministic ordering: (document_id, chunk_id).
    No score-based ranking - keeps exhaustive results neutral.
    """
    return (document_id, chunk_id)

4.3 HYBRID RRF IMPLEMENTATION (Critical Correctness)
----------------------------------------------------

BUG WARNING: The naive approach of using Python list(lex_ids).index(chunk_id)
is WRONG because sets have no ordering. This produces random ranks and breaks
RRF.

DEFAULT IMPLEMENTATION: SQL CTE (not Python)

Reasons to prefer SQL CTE:
- Deterministic (same query = same results)
- Faster (no large set pulls into Python)
- Works for both conversational and thorough candidate pools
- Memory-efficient for large result sets

PRIMARY IMPLEMENTATION: SQL CTE for RRF

WITH lex_ranked AS (
    SELECT chunk_id, 
           ROW_NUMBER() OVER (ORDER BY ts_rank_cd(tsv, query) DESC, chunk_id) as rank
    FROM chunks c, websearch_to_tsquery(%(query)s) query
    WHERE c.tsv @@ query
    LIMIT %(lex_limit)s
),
vec_ranked AS (
    SELECT chunk_id,
           ROW_NUMBER() OVER (ORDER BY embedding <=> %(embedding)s::vector, chunk_id) as rank
    FROM chunks
    WHERE (1 - (embedding <=> %(embedding)s::vector)) >= %(threshold)s
    LIMIT %(vec_limit)s
),
combined AS (
    SELECT COALESCE(l.chunk_id, v.chunk_id) as chunk_id,
           l.rank as rank_lex,
           v.rank as rank_vec,
           1.0 / (%(rrf_k)s + COALESCE(l.rank, 100000)) + 
           1.0 / (%(rrf_k)s + COALESCE(v.rank, 100000)) as rrf_score
    FROM lex_ranked l
    FULL OUTER JOIN vec_ranked v ON l.chunk_id = v.chunk_id
)
SELECT *, ROW_NUMBER() OVER (ORDER BY rrf_score DESC, chunk_id) as final_rank
FROM combined
ORDER BY rrf_score DESC, chunk_id
LIMIT %(max_hits)s;

For intersection mode, replace FULL OUTER JOIN with INNER JOIN.

FALLBACK: Python implementation (for debugging or special cases only)

If needed for debugging, a Python fallback exists that:
- Executes two SQL queries with explicit ROW_NUMBER() ranks
- Builds rank dicts from SQL results (NOT from set.index())
- Computes RRF scores in Python
- Verifies SQL CTE matches Python output in tests

The Python fallback must NEVER use list(set).index() - always carry ranks
explicitly from the SQL queries.

5.1 LAZY VS EAGER ENRICHMENT STRATEGY
-------------------------------------

CRITICAL PERFORMANCE ISSUE: Eager enrichment (loading chunk text, scanning for
phrases in Python, adding filter-pass entries for every chunk) will melt at
scale.

Solution: Tiered Enrichment

| Tier | When         | What                                     | Cost              |
|------|--------------|------------------------------------------|-------------------|
| 0    | All results  | Hot columns from search (scores, ranks)  | O(1) per chunk    |
| 1    | All results  | Entity IDs from entity_mentions (batch)  | O(N) single query |
| 2    | Top N only   | Full entity details for LLM synthesis    | N = summ_limit    |
| 3    | On-demand    | Phrase positions, full text highlights   | Only when expanded|

Filter pass handling: Store once at run level, NOT per-chunk:
- retrieval_runs.applied_filters JSONB - list of filters applied to query
- Per-chunk traces only store scope_passed: bool (always TRUE for included)
- Only store failed_filters if explicitly computing exclusion analysis

HARD RULE: Never load full chunk text for more than summarization_limit chunks
during execution, even in thorough mode. Thorough mode returns all chunk IDs
but does NOT do LLM prep work for all of them.

5.4 FILTER PASS STORAGE
-----------------------

Problem: Storing "pass" for every filter on every chunk is repetitive and heavy.

Solution: Store applied filters at the retrieval_run level, not per-chunk.

  ALTER TABLE retrieval_runs ADD COLUMN applied_filters JSONB;
  -- Example: ["FILTER_DATE_RANGE(1945-01-01,1950-12-31)", "FILTER_COLLECTION(silvermaster)"]

Per-chunk traces only store:
- scope_passed: bool DEFAULT TRUE - always TRUE for included results
  (Renamed from filters_passed to clarify semantics)
- failed_filters: list[str] - only populated if explicitly computing exclusion
  analysis ("why didn't X appear?"), which is a separate feature

Note: Any chunk in the result set has passed scope filters by definition.
So scope_passed is redundant but kept for schema clarity. Consider removing
later if it adds no value.

5.5 PAGE RANGE STABILITY
------------------------

Issue: string_agg() for page ranges needs deterministic ordering.

  -- WRONG (ambiguous ordering):
  SELECT string_agg(p.logical_page_label, '-') as page_range ...

  -- CORRECT (explicit ordering by span_order):
  SELECT string_agg(p.logical_page_label, '-' ORDER BY cp.span_order) as page_range
  FROM chunk_pages cp
  JOIN pages p ON cp.page_id = p.id
  WHERE cp.chunk_id = %(chunk_id)s
  GROUP BY cp.chunk_id

Ensure span_order exists and is populated correctly in chunk_pages.
